[ash](https://github.com/keix/ash) は、C11 で書いている ANS Forth の処理系です。C では Forth が話せるようになるまでの最小限のカーネルだけを書き、残りは Forth で書いています。

名前は、全てを焼き尽くしたあとに残る灰（Ash）から取りました。要らないものを燃やし尽くしたあとに残るものだけをカーネルにする、という意味です。

目指しているのは、**最も単純で力強く、明確な境界を持つプログラム**です。

今どき C で処理系を書くと、「Rust で書けば安全なのに」と言われそうです。確かに Rust なら安全に書くこともできます。それでも、言語を選んだあとも、処理系がどこで何を保証するかは自分で決める必要があると考えています。その話は後半に書きます。

## 境界は三つ

Ash は、三つの境界だけで説明できるように作っています。

```text
source  ──────────────▶  token
════════ semantic boundary ════════
outer interpreter  ───▶  xt
════════ execution boundary ═══════
threaded engine  ─────▶  machine
══════ optimization boundary ══════
JIT
```

- **意味の境界**: トークナイザは空白で区切るだけで、意味は付けません。トークンが辞書の語になるのか、数になるのかは、外側のインタプリタが決めます。
- **実行の境界**: 「何を実行するか」を決める部分と、「どう実行するか」を分けます。間にあるのは実行トークン（xt）だけです。
- **最適化の境界**: JIT は、この線より下にあるものしか触りません。上から見たときの意味は変えません。

Forth にはほとんど構文がありません。Ash は AST を組み立てず、トークンを読み進めながら、コンパイル時の語がスレッドコードを辞書に書き込みます。コンパイル中でもトークンの流れは同じで、変わるのは、トークンを受け取ったインタプリタの反応だけです。境界をはっきり引くには、最高の言語でした。

## C で書く意味

C で書いた語は、Forth で書けないから C にあるのではありません。**ここが境界だと決めたから** C にあります。

| | 語数 |
|---|--:|
| ANS Core の語 | 133 |
| そのうち C で書いた語 | 50 |
| そのうち Forth で書いた語 | 83 |

C に残しているのは、スタック操作、算術、メモリアクセス、入出力、スレッドコードの分岐といった機械との境目の語と、`:` や `create`、`parse-name` のように Forth が Forth を定義し始めるのに要る語です。

`if` や `begin` のような制御構文も、C ではありません。`branch` と `0branch` を辞書に書き込むか、分岐先を `here` で記録するだけの、即時実行の語です。

```forth forth/core.fs
: if    ['] 0branch , here 0 , ; immediate
: then  here swap ! ; immediate
: else  ['] branch , here 0 , swap here swap ! ; immediate

: begin here ; immediate
: until ['] 0branch , , ; immediate
```

`if` は分岐命令と空きのセルを書き、空きの番地をスタックに残します。`then` はその番地に今の位置を書き戻します。これで全部です。

### カーネルを燃やす

この境界は、下へ下げていくものだと考えています。C から Forth へ移すことを、Ash では「燃やす」と呼んでいます。今までに燃やしたのはこの三つです。

- `.`: 数の表示は、`<#` `#s` `#>` を使う Forth の定義になりました
- `/` と `mod`: `sm/rem` を通す Forth の定義になりました
- REPL: 一行読んで、解釈して、`ok` を返すループも Forth です

割り算を燃やしたときは、ゼロ除算の扱いも変わりました。C のままだとプラットフォームの挙動を引き継いでクラッシュしていましたが、今は Forth の例外として `-10` を投げます。

```forth forth/core.fs
: sm/rem
  dup 0= if -10 throw then
  2dup xor 0< >r
  over 0< >r
  abs >r dabs r> um/mod
  swap r> if negate then swap
  r> if negate then ;
```

```text
: sq dup * ;  ok
7 sq . 49  ok
1 0 / uncaught throw: -10
```

C で書く量が減るほど、Ash が何でできているかが見えやすくなります。今の行数はこうです。

| ファイル | 行数 | 役割 |
|---|--:|---|
| src/*.c（JIT 以外） | 1,688 | カーネル。辞書、スタック、トークナイザ、プリミティブ |
| src/jit.c | 1,702 | x86_64 の JIT |
| forth/core.fs | 689 | Forth で書いた語の全部 |

## 例外も Forth で書く

`CATCH` と `THROW` は、C の `setjmp` と `longjmp` を使っていません。Forth のリターンスタックだけで書いています。

```forth forth/core.fs
: catch
  sp@ >r handler @ >r rp@ handler !
  execute
  r> handler ! r> drop 0 ;

: throw
  ?dup if
    handler @ 0= if uncaught then
    handler @ rp! r> handler !
    r> swap >r sp! drop r>
  then ;
```

`catch` は、今のスタックポインタをリターンスタックに積んでから実行します。`throw` は、積んでおいたポインタを書き戻すだけです。C のカーネルが用意したのは `sp@ sp! rp@ rp!` の四つだけでした。

これが成り立つのは、内側のインタプリタが一つの約束を守っているからです。**コロン定義の戻り先は Forth のリターンスタックに積み、コロン定義を呼ぶたびに C の実行ループへ再帰することはありません。**

```c src/exec.c
void
docol (vm_t *vm, xt_t xt)
{
  jit_count (vm, xt);
  rpush (vm, (cell_t)vm->ip);
  vm->ip = (xt_t *)(xt + 1);
}
```

`docol` 自体は C の関数で、JIT のための回数も数えます。それでも、戻り先は Forth のリターンスタックに積んで命令ポインタを動かすだけで、呼ばれた語が終わるまで C のフレームを残しておくことはありません。Forth の呼び出しが深くなっても、C のスタックは深くなりません。だから、二つのスタックポインタを書き戻せば、それが非局所的な脱出になります。

例外の意味は機械の境界より上に置きたかったので、C の仕組みは使いませんでした。

## コードフィールドを一つ書き換える JIT

辞書の各語は、名前のあとに `does` と `code` の二つのセルを持ちます。xt は `code` を指す番地で、本体はその次のセルから始まります。

```text
link | flags | name… | does | code | body…
                             ▲ xt   ▲ >BODY = xt + 1
```

語の実行のしかたを変えるには、`code` を書き換えます。触るのはこの一つのセルだけです。

スレッドコードで動いていたコロン定義でも、`code` をネイティブコードに差し替えれば、それだけで JIT 済みになります。呼び出し側はいつも `code` を通って入ってくるので、呼び出し側は何も変わりません。スレッドコードの語とネイティブの語は、混ざったままで動きます。

JIT 側も、例外と同じ約束を守ります。ネイティブコードから別の語を呼ぶときも、戻り先は Forth のリターンスタックに積みます。C のスタックには積みません。そのため `throw` は JIT のことを知らなくても、ネイティブの戻り先ごと捨てられます。

> JIT が例外に合わせるのであって、例外が JIT を知ってはいけない。

どの語を JIT するかは、回数を数えて決めます。呼び出しは xt ごとに、ループの後ろ向きの分岐は分岐先の番地ごとに数え、512 回に達したところで、その語のコンパイルを試みます。対象の語が見つからないときや、コード領域に空きがないときは、そのままスレッドコードで実行を続けます。

ループの途中でコンパイルに成功したときは、OSR 用のスタブを通って、分岐先からネイティブコードで実行を再開します。分岐先ではスタックがすべてメモリ上にあるので、途中から乗り換えても状態を組み立て直す必要がありません。

カウンタは辞書の中に置いていません。どの語が熱いかは最適化の都合であって、言語の一部ではないからです。

### 速さ

素朴な再帰で書いた `fib(40)` で比べました（約 3 億 3,000 万回の呼び出し）。

```forth bench/fib.fs
: fib dup 2 < if exit then dup 1- recurse swap 2 - recurse + ;
40 fib . cr
```

| 処理系 | fib(40) |
|---|--:|
| Ash（JIT） | 0.93 s |
| Ash（JIT なし） | 8.16 s |
| gforth | 1.08 s |
| gforth-fast | 0.50 s |
| Python 3.14 | 7.05 s |

Ash は `-O2` でビルドし、gforth と同じセッションで 3 回測った中央値です。Python だけは別のセッションで測った数字です。

JIT なしの Ash は 8.16 秒で、Python 3.14 より遅いところから始まりました。最初の目標は Python を抜くことでした。今は JIT で gforth を抜き、gforth-fast の倍ほどのところまで来ています。

## 規格に合わせる

Ash は ANS Forth の Core と Core Extensions の語をすべて実装していて、Forth 2012 のテストスイートの Core と Core Extensions のテストを通ります。

```sh
make test       # C と Forth のテスト。JIT あり・なし・既定の三通り
make test-ans   # Forth 2012 のテストスイート
```

Forth のテストは、JIT を常に使う、まったく使わない、熱くなったら使う、の三つのモードで同じものを流します。どのモードでも結果が変わらないことが、最適化の境界が守られている証拠になります。

## 安全は境界で決まる

C で書いている以上、Ash は未定義動作と隣り合わせです。実際に、最近こんなバグを直しました。

- **整数のオーバーフロー**: `+ - *` を符号付きの `cell_t` で計算していたので、あふれると未定義動作でした。しかも `DO` ループは、仕組み上わざとあふれさせて動いています。UBSan がテスト全体で警告を出したので、`uintptr_t` で計算して戻すようにしました。
- **配列の外の読み出し**: 空のスタックで `drop` すると、配列の一つ外を読んでいました。ASan で見つけて、スタックの両端に余白を足しました。
- **スタックのはみ出し**: 暴走したループや深い再帰が、スタックの隣にある配列を黙って壊していました。今はスタックを `mmap` で確保し、両端に読み書きできないガードページを置いています。ガードページにアクセスした時点で止まり、どの端を越えたかを表示して終了します。

正直に言うと、このうち最初の二つは safe Rust なら起きないバグです。safe Rust では、整数があふれても未定義動作にはならず、配列の範囲外を読み出すこともできません。

それでも、Rust なら Ash が安全になるとは思っていません。

safe Rust が保証するのは、メモリ安全とデータ競合がないことです。それは下にある `unsafe` のコードが正しいという前提の上に成り立っていて、`unsafe` は Rust が言語に組み込んだ**境界**です。

そして Ash の一番危ない仕事は、その境界の外にあります。

- Ash では、`@` と `!` がセルの値をホストのアドレスとして使い、直接読み書きします
- JIT は、自分で書いた機械語に制御を渡します

この実装方式を Rust で再現するなら、生ポインタの逆参照には `unsafe` が必要です。生成した機械語へ跳ぶことも、コンパイラには検証できません。どちらも Rust で書けば `unsafe` の中に置くことになります。

`throw` は少し違います。Forth のスタックを配列で、その位置をインデックスで表せば、スタックを書き戻すこと自体は safe Rust でも書けます。`throw` を正しく動かしているのは言語ではなく、前半に書いた約束です。Forth の語から語への戻り先は Forth のリターンスタックに置き、C のスタックには積まない。実行エンジンと JIT がこれを守っているから、`throw` は JIT を知らなくても動きます。

もう一つ、言語が決めてくれないこともあります。オーバーフローしたら折り返すのか止まるのか、ゼロで割ったらどうするのか。Rust でも `wrapping_add` を使うかどうかは自分で選びますし、ゼロ除算のパニックは Forth の `-10` にはなりません。それは処理系が決める意味です。

Ash では、境界を C の中に手で引いています。

- 前提は隠さずに宣言する: 関数ポインタが 1 セルに収まることは `_Static_assert` で確かめています
- 境界で検出する: スタックの深さは語と語の間で調べ、一つの語の中ではみ出したらガードページで止めます
- 道具で確かめる: セッションのテストを ASan と UBSan の上で流したときは、どちらからも報告はありませんでした

Rust では、safe な呼び出し側から `unsafe` の前提を破れないようにするのは、`unsafe` を包む API の実装者の責任です。その条件が満たされていれば、呼び出し側は safe Rust の保証を受けられます。Ash では、語の実行前後で何が成り立つべきかを決め、実行時の検査とテストで確かめています。こちらの保証は、自分で引いた境界と、それを確かめる仕組みの分しかありません。

どちらも、境界をどこに引き、そこで何を約束するかを決めることから始まります。

## つぎにやること

- カーネルをさらに燃やして、C で書く語を減らす

C で書くのは、そこに境界を定義するという意味になります。
