このサイトは今まで Hugo (Go) で作っていましたが、ソースが手元になくビルド結果だけが残っていました。せっかく作り直すなら、Lua で書いて [moonquakes](https://github.com/keix/moonquakes) を GitHub Actions で動かしてみたい。そう思って、静的サイトジェネレータを一から書くことにしました。

## なぜ自作するのか

既製のジェネレータは便利ですが、記事を書くだけなら必要な機能は多くありません。Markdown を HTML にして、テンプレートに流し込み、一覧と RSS を作る。**それだけなら数百行で書ける**はずです。

- 依存はランタイム（moonquakes）だけ
- 処理を全部読める大きさに保つ
- ビルドそのものを処理系のテストにする

結果として、Lua は全部で 1,200 行ほどになりました。数百行というには少し多いですが、一晩で読み切れる量には収まっています。

## ファイル構成

| ファイル | 行数 | 役割 |
|---|--:|---|
| build.lua | 507 | エントリ。記事を集めて、各ページと RSS・sitemap を書き出す |
| lib/markdown.lua | 319 | Markdown → HTML。目次もここで作る |
| lib/template.lua | 149 | Mustache 風のテンプレートエンジン |
| lib/highlight.lua | 96 | コードの色付けと行番号 |
| lib/frontmatter.lua | 65 | 記事の先頭にある YAML のサブセット |
| lib/fs.lua | 59 | ファイル操作。中身はシェルコマンド |
| site.lua | 49 | サイトの設定 |

記事はすべて、自分の実装ごとのシリーズに連番で置きます。`posts/moonquakes/2026-11-05-1.md` なら、ファイル名の日付が公開日に、番号が URL（`/posts/moonquakes/1/`）になります。

## Markdown をパターンだけで変換する

LPeg は C モジュールなので使いません。Lua のパターンと `string.gsub` だけでパーサーを書きます。ブロック要素は 1 行ずつ見て判定します。たとえば見出しはこうです。

```lua lib/markdown.lua
local function heading(line)
  local marks, text = line:match("^(#+)%s+(.-)%s*$")
  if marks and #marks <= 6 then
    text = text:gsub("%s+#+$", "")
    return #marks, text
  end
end
```

### インライン要素は「退避」が大事

強調やリンクは、順番に `gsub` をかけていくだけで変換できます。ただし素直にやると、コードスパンの中の `*` まで強調になってしまいます。

そこで、変換し終わった HTML はいったん表に退避して、本文には `\1` 番号 `\2` という目印だけを残します。最後に目印を元に戻せば、退避した部分にはもう誰も触れません。

```lua lib/markdown.lua
local stash = {}
local function keep(html)
  stash[#stash + 1] = html
  return "\1" .. #stash .. "\2"
end

-- Code spans first: nothing inside them is markup.
s = s:gsub("(`+)(.-)%1", function(_, code)
  return keep("<code>" .. escape(code) .. "</code>")
end)
```

コードスパン、エスケープ、リンクの順に退避していき、最後に強調を変換します。順番を決めるだけで、構文木を作らずに済みました。

> Simple is better than complex.

## 二つの処理系で同じ出力になるか

いちばん楽しみにしていたのがここです。このジェネレータは、公式の Lua 5.4 でも moonquakes でも動きます。それなら、**二つで出力が 1 バイトでも違えば、どちらかがおかしい**ことになります。

```sh
make check
# lua5.4 と moonquakes でビルドして diff -r する
```

実際に、この差分テストで moonquakes の違いが二つ見つかりました。

### string.find が値を一つしか返さない

`("hello world"):find("wor")` は本来 `7, 9` を返します。ところが moonquakes では、`print` の引数のように**複数の値をそのまま受け取る場所**で、開始位置の `7` しか返っていませんでした。

```lua
print(("hello world"):find("wor"))
-- Lua 5.4:    7    9
-- moonquakes: 7
```

`local s, e = str:find(...)` のように受け取る数を決めて代入すれば正しく動くので、ジェネレータ側はすべてこの書き方にそろえてあります。

### os.time が時刻を UTC として扱う

`os.time{year = 2026, month = 11, day = 5}` は、本来ローカル時刻として解釈されます。moonquakes では UTC として扱われていて、日本時間ではちょうど 9 時間ずれていました。RSS の日付がずれたことで気づきました。

RSS に必要なのは曜日だけなので、`os.time` を使わずに計算することにしました。

```lua build.lua
local offsets = { 0, 3, 2, 5, 0, 3, 5, 1, 4, 6, 2, 4 }
local yy = m < 3 and y - 1 or y
local wday = (yy + yy // 4 - yy // 100 + yy // 400 + offsets[m] + d) % 7
```

どちらも、普通にサイトを作っているだけでは気づかなかったと思います。ビルドがそのまま処理系のテストになる。最初に掲げた目標が、さっそく役に立ちました。

## Nix で処理系ごと固定する

ジェネレータが自作の処理系に依存している以上、moonquakes のバージョンもきちんと固定したいところです。そこで、このリポジトリを Nix の flake にして、moonquakes を入力として取り込みました。

```sh
nix build .#site   # moonquakes をコンパイルして、そのままサイトをビルド
```

nixpkgs と Zig 0.15.2 も、moonquakes 自身の `flake.lock` に合わせています。手元でも GitHub Actions でも、まったく同じコンパイラでビルドされます。

一つだけハマりました。Nix のサンドボックスの中では、Zig がシステムの libc を判別できません。そのため、存在しない musl のローダを指したバイナリができて、起動すらできませんでした。ターゲットを glibc と明示し、`autoPatchelfHook` でローダの場所を Nix のものに書き換えて解決しています。静的リンクにする手もありましたが、`package.loadlib` で C モジュールを読めるように動的リンクのままにしました。

## 書く環境

記事を書くときは `make dev` だけです。保存するたびにビルドし直して、開いているブラウザが勝手にリロードされます。

仕組みはとても単純です。ビルドのたびに `/__live` というファイルに時刻を書き込み、ページ側のスクリプトがそれを 0.8 秒ごとに見に行きます。値が変わったらリロードする、それだけです。WebSocket もファイル監視のライブラリも使っていないので、`sh` と `find` があれば動きます。

## つぎにやること

- ディレクトリの列挙は今のところ `ls` に頼っています。moonquakes 側に `os.listdir` を足すかどうか考えます
- `string.find` と `os.time` の二つは、moonquakes 側で直します
- 直ったら、ジェネレータの回避策を外して、`make check` で確かめます

処理系を直すとサイトのビルドで確かめられて、サイトを作ると処理系のバグが見つかる。しばらくは、この往復で眠れない夜を過ごせそうです。
